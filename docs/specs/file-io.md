# Spec: File I/O, saving and external changes

Covers FR-DOC-01, FR-DOC-02, FR-DOC-05, FR-DOC-06, FR-DOC-07, FR-UI-04 (storage), F-FILE-01, 04–07, 09, N-REL-01 and N-UX-01.

## 1. Opening

- `tpt <path>`: open the file; if it does not exist, start an empty document and create the file on first save. Parent directories must exist.
- `tpt --version` prints the version and `tpt --help` the usage, and each exits without opening a file; any other argument starting with `-` is refused with the usage and opens nothing, so a flag is never taken for a file name; a file named like one is opened as `./-name` (D-113). More than one argument, or an empty path, is refused with the same usage.
- `tpt` with no path: create a new file `/tmp/taskpaper-<YYYYMMDD-HHMMSS>.taskpaper` holding the demo document and open it (FR-DOC-05, D-27). A name already taken, as by a second start in the same second, gets `-2`, `-3` and so on before the extension, and only the user may read the file. The status line marks it as a temporary file until it is saved elsewhere with Save As.
- **Demo document:** a TaskPaper file kept in the repository at `app/assets/demo.taskpaper` and compiled into the binary. It holds a few toy projects (for example a trip, a small software release and a reading list) that between them use every block type, tag and feature the app implements, each where a person would naturally use it, so trying a feature needs no setup. Dates in it are written relative to today when the file is created (a placeholder such as `@due({today+1})` is resolved to `YYYY-MM-DD`), so due, overdue and Today items stay meaningful. It must parse as a canonical outline ([file-format.md §3.1](file-format.md#31-canonical-outlines)); a test checks that and that every block type and supported tag implemented so far occurs in it.
- Read errors, non-UTF-8 content and permission errors are shown on stderr before the TUI starts, and the app exits non-zero.
- Read-only files open read-only; editing commands report "read-only" in the status line.

## 2. Saving

**Atomic write** (F-FILE-04):
1. Serialize the document ([file-format.md §6](file-format.md#6-serialization)).
2. Write to a temp file in the same directory (`.<name>.tpt-XXXX`), `fsync` it.
3. Copy the original file's permissions.
4. Rename over the target; `fsync` the directory.
5. Record the new file's version (its length and a hash of its bytes) as the "known disk state".

If the target is a symlink, write through to the resolved path so the link is preserved.

**When** (FR-DOC-02, D-15): there is no manual save.
- 1 s after the last change (configurable `autosave_delay_ms`, minimum 100).
- On quit and on `SIGTERM`/`SIGHUP`.

**Save As** (FR-DOC-06): prompt for a path (with `~` expansion and completion of directories); if the file exists, confirm overwriting. Write the document there with the atomic routine below, then make it the open file: autosave, file watching, backups and view-state persistence switch to the new path. The previous file is left as it was.

Saving runs on a background thread with a snapshot of the document, which it serializes and hashes there, so the UI never waits on disk or on serializing a large file (N-UX-01, N-PERF-02). The status line shows `●` while there are unsaved changes and an error badge if the last save failed. A save into a folder that does not exist says `the folder <folder> does not exist`, the words opening uses (D-121); any other failure gives the system's reason. A failed save keeps retrying on the next change and on quit; quit with unsaved changes after a failed save asks before exiting: the status line says that quitting again exits without saving, until the next change or a successful save.

**Daily backups** (FR-DOC-07, F-FILE-09, D-22):
- **Where:** `$XDG_DATA_HOME/taskpaper-terminal/backups/`, or `~/.local/share/taskpaper-terminal/backups/` when it is unset, on macOS too. Backups are user data rather than disposable state, so they go under the data directory, not `$XDG_STATE_HOME`. The `backups.dir` setting overrides the folder (for example `~/.taskpaper-terminal/backups`); `~` is expanded.
- **One folder per file:** `<file name>-<hash>/`, where `<hash>` is the 64-bit FNV-1a hash of the file's canonical path as 16 lowercase hex digits. Two `todo.taskpaper` files in different directories get different folders; the hash is written by hand, so it is stable across Rust releases (std's `DefaultHasher` is not). The folder also holds `source-path.txt` with the full path, so a person can tell which file it belongs to.
- **When:** on opening the file, and before the first save of each new local day for a session left running past midnight. If the folder has no copy dated today, copy the file as it is on disk, before the app writes anything, to `<YYYY-MM-DD>.taskpaper` (local date) with the atomic-write routine above. So each day's copy is the file as it was before that day's first change by the app.
- **Skipped:** when the file does not exist on disk or is empty (a new path), and for the `/tmp` document of §1 until it is saved elsewhere, and when the on-disk bytes equal the newest daily copy, so a file left unchanged for weeks does not use up its retention on duplicates.
- **Retention:** keep the newest `backups.keep` daily copies per file (default 30), newest by the date in the name; after writing a daily copy, delete the oldest ones beyond that. Conflict copies (§3) are pruned the same way but counted separately, so conflicts never push out daily copies. Nothing is pruned while backups are disabled. Folders of files that no longer exist are left alone.
- **Settings** (FR-SET-01): `backups.enabled` (default `true`), `backups.dir` (default unset, meaning the path above), `backups.keep` (default 30, minimum 1). Changing the folder takes effect on the next backup; existing copies are not moved.
- **Failures** never block opening or saving: the status line shows a warning once per session with the reason, and the next day's check tries again.
- **Save As** switches backups to the new path, which gets its own folder.
- There is no restore command; a backup is a plain `.taskpaper` file that `tpt` opens directly.

## 3. External changes

Watch the file's folder with the `notify` crate (debounced, 200 ms), since many editors save by renaming a new file over the old one; each burst of changes there reads the file again, as does regaining terminal focus and every save. A read compares the file's version (length and hash of its bytes) with the known disk state, so reads of an unchanged file, such as after the app's own save, do nothing.

When the version on disk differs from the known disk state (OQ-16 default):
- **No unsaved local changes:** reload silently, keep each pane's focus, zoom, zoom history and collapsed blocks on the same blocks where they can be re-matched (same path of first-line texts from root, without tags and counting equal texts among siblings; else focus and zoom go to the nearest surviving ancestor and a fold is dropped), clear the undo history, whose item ids no longer apply, and show "Reloaded (changed on disk)". A reload does not interrupt editing (D-104): edit mode carries on with the block being edited where it is re-matched, its text and tags as the reloaded line has them and the caret at the same column, as does editing that a command of the command menu would resume (D-50); the date prompt stays open on the blocks it sets that are re-matched; Go to Symbol, Go to Project and Move to list the reloaded blocks, keeping their query and the highlighted block where it is re-matched, Move to's Home included; the context menu and edit mode's command menu list their commands for the reloaded blocks, keeping their filter while it matches one and the highlighted command while it is offered. Each ends or closes only when what it acts on is gone: the block being edited, every block the date prompt sets, every block Move to would move, or whatever the context menu offers commands for. The Edit Node dialog closes, changing nothing, since its draft is of the block as it was. Nothing typed is lost: the edited text is written to the document as it is typed, and a change on disk while it is unsaved opens the prompt below instead.
- **Unsaved local changes:** pause autosave and prompt, saying "Your changes are not saved yet.": *Keep mine* (first write the on-disk version to the file's backup folder as a conflict copy, then overwrite disk at once; editing carries on in the same block with the caret where it was, since nothing local changes, in the spirit of D-104), *Take theirs* (write the local version there as a conflict copy, then reload as above; like any reload it does not interrupt editing, which carries on in the block found again by its path with the caret where it was and ends only when that block is no longer found, D-123; a block is looked for by its path as the file last held it before the unsaved changes, so the block whose text was being typed is found again), *Show diff* (a read-only line diff from the file on disk to the local version, three unchanged lines around each change; it is shown in the prompt, which grows to the size of a prompt, until panes arrive in M5). In a terminal too narrow for its lines the prompt wraps them, its message between words and its keys between choices, and keeps rows for every key first, since it has no `Esc` and its keys are the only way to learn how to answer. The status line then says, in the prompt's own words, `Kept mine; theirs is in <copy>` or `Took theirs; mine is in <copy>`, the copy's path with the home folder as `~` (D-122). A conflict copy is named `<YYYY-MM-DD>-<HHMMSS>-conflict.taskpaper` (local time; a later second when that name is taken), is written even when backups are disabled, and failing to write it cancels the choice and shows the error, so the discarded version is never lost. A further change on disk while a choice waits for its copy cancels the choice, and the prompt then offers the newer version. Quitting, or being told to end, while the prompt is open leaves the file on disk as it is and writes the local version to a conflict copy; a quit ends once the copy is written, then prints `tpt: left theirs on disk; mine is in <copy>` once the terminal is restored, as a crash prints the recovery file's path (§4), and, when the copy fails, writes the local version to a recovery file (§4) instead and prints its path the same way; only when that fails too does a quit ask as after a failed save, while being told to end ends anyway (D-124). A conflict copy that fails while writing in the backups folder says which: `conflict copy failed in <folder>: <reason>`, the folder's home as `~`. A file deleted on disk still gets its conflict copies in its backup folder. The prompt opens on its own, maybe while the user types, so its choices take `Ctrl` keys no typing sends (D-115): [keybindings.md §4](keybindings.md#4-other-contexts).
- **Not UTF-8 on disk:** the file cannot be reloaded or taken, so the prompt opens even without unsaved local changes, saying "The file on disk is not UTF-8, so it cannot be reloaded." when there are none (D-99), and *Take theirs* is refused with the reason, `cannot take theirs: <reason>`; *Keep mine* overwrites it after its conflict copy, and the diff shows its invalid bytes as `�`.
- **File deleted or moved:** keep the buffer, mark it "not on disk", and recreate the file on next save.

Saves read the file immediately before renaming; if its version is no longer the one the save expected, the save is aborted, its new file removed, and the version on disk handled as above, which with the unsaved changes the save was for opens the conflict prompt. This prevents overwriting edits made by TaskPaper 3, a sync tool or another editor. A file that cannot be read then fails the save with the reason, as any save failure does; a read that fails while checking is not reported, since the next save reports it.

## 4. Crash safety

- Install a panic hook that restores the terminal first, then writes the current serialized document to `$XDG_STATE_HOME/taskpaper-terminal/recovery/<name>-<timestamp>.taskpaper` and prints its path (N-REL-01).
  - Only a document holding changes its file lacks (a save is due or under way, or the last one failed) is written. Disk work already asked for, such as a save under way, finishes first, so that it cannot change the file after the recovery file and stop it from being offered.
  - The folder is under `~/.local/state` when `$XDG_STATE_HOME` is unset, on macOS too.
  - `<name>` is the name of the file's backup folder (§2), `<file name>-<hash>`, so two files with one name never get each other's recovery files; a document without a file is `untitled`. `<timestamp>` is the local time as `YYYYMMDD-HHMMSS`, a later second when that name is taken, so a recovery file never replaces another.
  - The recovery file gets the file's permissions. The app never deletes recovery files.
- On start, if a recovery file newer than the target exists, offer to open it. Before the terminal UI starts, the app names the newest such file and asks `Open the file with these changes? [y/N]`. `y` or `yes` first writes the target as it is on disk to a conflict copy (§3), since it may have changed after the document was read from it, and refuses to open when that copy fails; it then opens the target showing the recovery file's document as unsaved changes, so it is saved over the target like any change, after the daily backup (§2); once the target is saved, the offer stops. Any other answer opens the target as it is. A recovery file written at the same time as the target counts as newer, because file times can be too coarse to tell a save and a crash right after it apart.

## 5. View-state persistence

Restores the pane layout (FR-UI-04, OQ-05 default A). Fold state is not persisted (D-26).

- File: `$XDG_STATE_HOME/taskpaper-terminal/views.json`, or under `~/.local/state` when it is unset, on macOS too, like the recovery folder (§4). It maps each file's canonical path (its absolute path while it does not exist yet) to its layout, and only the user may read it, since it holds text of the outlines.
- Stored per file: the panes in order with their history and the position in it of their location, focused block, width and show-completed setting; the focused pane; the order the user gave the Today view's entries (D-57), as the blocks placed in it, left out while there is none. A layout saved before D-79 also holds whether the sidebar showed, which is ignored.
- Blocks are stored as **text paths**: the list of first-line `text` values, without tags, from the top level down to the block, each with its index among equal-text siblings, the same matching as a reload (§3).
- On load, each path is re-matched; anything that doesn't match is dropped silently: a history entry whose zoom block is not found leaves the history, and two visits of one location brought together by that become one; a pane whose location is not found shows home; a block of the Today view's order not found leaves it; a focused block not found gives way to the first block under the title, as in a new pane, and one that does not show, which the Today view only tells once the frontend gives the date, moves as when a focus stops showing ([navigation.md §2](navigation.md#2-focus-and-motion-fr-nav-01)). View state never blocks opening a file: a missing or unreadable `views.json`, or a layout in it that cannot be read, opens the file as without one.
- Written on quit and on save, with the same atomic-write routine, keeping the other files' layouts; a `views.json` that cannot be read as a set of layouts is replaced. A failure to write it is not reported. The temporary file of §1 has no layout stored, since no later launch opens it; after Save As the layout is stored for the new path.
